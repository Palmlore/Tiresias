# Zetaris

Tiresias runs against a **local Zetaris** (vendor bundle `zetaris-platform`, image tag `2.4.3-v2.4.3.1-hackathon`), installed outside this repository by following the vendor README. REST is at `http://localhost:8888/api/v1.0`.

## What gets registered

`sql/` holds Lightning SQL templates with `{{placeholders}}` and no secrets. One file is one statement; `--` comment lines are stripped before it runs.

| File | Creates | Per |
|---|---|---|
| `00_database.sql` | Lightning database `TIRESIAS_SEC` | once |
| `01_container.sql` | SchemaStore container `tiresias` | once |
| `10_companyfacts_table.sql` | REST table `TIRESIAS_SEC.<ticker>_facts_raw` over SEC companyfacts | entity |
| `11_submissions_table.sql` | REST table `TIRESIAS_SEC.<ticker>_submissions_raw` over SEC submissions | entity |
| `12_cache_table.sql` | `CACHE TABLE` on each raw table, so queries don't refetch the SEC response | raw table |
| `15_uncache_table.sql` | `UNCACHE TABLE`: releases a raw table's cache (never drops it) under `ZETARIS_MAX_CACHED_FACTS` and after the source scout | raw table |
| `13_tickers_table.sql` | Discovery: REST table `TIRESIAS_SEC.sec_tickers_raw` over SEC `company_tickers_exchange.json` (catalog `sec_tickers`) | once |
| `14_fulltext_table.sql` | Discovery: REST table `TIRESIAS_SEC.fts_<hash>_raw` over one EDGAR full-text search (catalog `sec_fulltext`; `http_encoding "JSON"`, the search answers 415 to the form-encoded request) | scout search |
| `20_concept_view.sql` | View `tiresias.<ticker>_<slug>` via the struct path `facts.us-gaap.<Concept>.units.USD` (no map explode) | entity × concept |
| `21_filings_view.sql` | View `tiresias.<ticker>_filings` (10-K / 8-K history with 8-K item codes) | entity |
| `22_tickers_view.sql` | Discovery: view `tiresias.sec_tickers` (cik, name, ticker, exchange), one row per ticker | once |
| `30_concept_series.sql`, `39_order_facts.sql`, `31_filings.sql`, `32_entities.sql`, `33_views.sql` | Read-only queries the agent runs | call |
| `34_tickers_by_symbol.sql`, `35_tickers_by_brand.sql`, `36_tickers_by_name.sql` | Discovery reads over `tiresias.sec_tickers`: by ticker/CIK (asked entity, scout's source), by brand word (scout's candidates), by name (asked entity) | call |
| `37_submissions_profile.sql` | Discovery read: one candidate's profile and filing history from its `<ticker>_submissions_raw` (registered on demand from `11_submissions_table.sql`) | call |
| `40_fulltext_total.sql`, `41_fulltext_hits.sql` | Discovery reads over one `fts_<hash>_raw`: the number of matching documents, then (only if non-zero) the filers, most documents first, with their forms and 8-K items | call |

Showcase entities: `ge` (CIK 0000040545), `gehc` (0001932393), `gev` (0001996810). Concepts and their view slugs are `CONCEPT_SLUGS` in [`zetaris.py`](../services/agent/src/tiresias_agent/adapters/zetaris.py), the same seven concepts as the offline sample. `Revenues` and `RevenueFromContractWithCustomerExcludingAssessedTax` are aliases: a revenue query unions whichever of the two views exist.

Placeholders: `{{ticker}}`, `{{cik10}}`, `{{concept}}`, `{{slug}}`, `{{table}}`, `{{forms}}`, `{{tickers}}`, `{{ciks}}`, `{{words}}`, `{{pattern}}`, `{{limit}}`, `{{endpoint}}` (a percent-encoded `sec_fulltext` URL built by `adapters.catalog.fulltext_endpoint`), and `{{sec_user_agent}}` (from `SEC_USER_AGENT`, required by SEC fair access; masked as `***` in traces). Every value is checked against a strict pattern before it is substituted.

## Apply

```bash
# needs ZETARIS_REST_URL, ZETARIS_ORG_ID, ZETARIS_API_KEY and SEC_USER_AGENT in the environment
cd services/agent
uv run python -m tiresias_agent.adapters.zetaris bootstrap        # one JSON line per statement
uv run python -m tiresias_agent.adapters.zetaris smoke            # entities, revenue facts, filings
uv run python -m tiresias_agent.adapters.zetaris smoke --sample   # same checks, offline
uv run python -m tiresias_agent.adapters.zetaris warm             # re-cache raw tables after a Zetaris restart
```

`bootstrap` is safe to run twice. Lightning SQL has no `IF NOT EXISTS` for databases, containers or REST tables, so an "already exists" reply is reported as `exists`; views use `CREATE OR REPLACE` and report `replaced`. A view on a concept the entity never reported fails with `FIELD_NOT_FOUND` and is reported as `absent` (for example `gev_goodwill_impairment`); the adapter only queries views that exist. These expected replies are traced `status: "success"` with `outcome: "exists"` / `"absent"` on the statement's `bootstrap:<step>` line (the same for discovery registrations), so only a real failure (bad SQL, auth, 5xx, timeout) shows `status: "error"`. Bootstrap never drops anything. To remove a REST table by hand use `DROP LIGHTNING DATABASE TABLE TIRESIAS_SEC.<table>` (not `DROP TABLE`), and a view with `DROP SCHEMASTORE VIEW <view> FROM tiresias`.

The cache is a session cache: after a Zetaris restart, run `warm` so the first query doesn't wait on the SEC fetch. `warm` lists the registered REST tables (`32_entities.sql`) and re-issues `CACHE TABLE` (`12_cache_table.sql`) for the raw tables, one statement at a time, and nothing else (no CREATE, no DROP). It takes them in priority order: the entities in `ZETARIS_WARM_ENTITIES` in the order given, each one's companyfacts then submissions (comma-separated object tickers as `object_ticker` names them, e.g. `brkb` for BRK-B; default `mmm,solv,ge,gehc,gev`: the demo company 3M and its spin-off Solventum, then the GE showcase; each name must match the same strict pattern as a `{{ticker}}` placeholder, otherwise `warm` fails before sending any SQL), the `sec_tickers` map, then other registered entities' facts and submissions, then submissions tables that only discovery registered; EDGAR full-text tables (`fts_<hash>_raw`) are never refetched. At most `ZETARIS_WARM_MAX_TABLES` (default 11: the five default entities' facts and submissions plus the ticker map) are re-cached; the rest are listed as `capped`. The cap is there because each cached companyfacts table holds Zetaris driver heap, and the bundle's driver has 2 GB: re-caching all 63 registered tables once ran it out of memory after about ten companyfacts tables (see Quirks, BACKLOG B-24). The default holds five companyfacts tables; raise the cap or lengthen the list with that limit in mind. Each statement may take `ZETARIS_WARM_TIMEOUT_SECONDS` (default 120; a cold refetch can pass the 20 s source timeout), without retry, within `ZETARIS_WARM_BUDGET_SECONDS` for the whole pass (default 600; later tables are `skipped`, `reason: "budget"`); two failures in a row stop the pass (`skipped`, `reason: "halted"`: Zetaris itself is likely down). It prints one JSON line per table (`warmed`, `absent`, `failed` with `recoverable`, `skipped`, `capped`) and the counts, and exits 1 if any table failed or was skipped. Each statement is traced as `warm:cache` (`success`; `outcome: "absent"` if the table was dropped after it was listed; `error` for a real failure), then one `warm` line: `success` (all warm), `degraded` (partial) or `error` (none warm).

**Bounded cache (BACKLOG B-24).** At most `ZETARIS_MAX_CACHED_FACTS` (default 5, 1..50) companyfacts tables stay cached per agent process. Before a `CACHE TABLE` on one more (`bootstrap`: a runtime registration or the CLI; `warm`), the adapter sends `UNCACHE TABLE` (`15_uncache_table.sql`) for the least recently used one (a query on a table counts as a use) that the current run does not need: never the run's asked entity or its Loop B counterparty (pinned while a run goes on), never one `warm` itself just warmed. If every cached table is needed the new one is cached anyway (`cache_cap: "exceeded"` on the bootstrap entry); `warm` instead lists further companyfacts tables as `capped` (`reason: "cache_cap"`). Discovery tables are released too: after the source scout, the candidate `<ticker>_submissions_raw` tables it cached and was not choosing and the `fts_<hash>_raw` tables are uncached, and at the end of a live run whatever discovery tables it still holds except the asked entity's; a released table is re-cached before its next read. Each `UNCACHE` is one `uncache` trace line with `table` and `reason`; a failure is logged and never fails a run. Nothing is dropped and registrations stay. The process only knows the tables it cached itself (not those cached before it started or by another process).

**Liveness probe.** Before a live run the agent sends `42_liveness.sql` (`SELECT 1 AS alive`: no table, no SEC fetch, but it needs a running SparkContext) with a 3 s timeout and no retry (`ZETARIS_LIVENESS_TIMEOUT_SECONDS`), and reuses the answer for `ZETARIS_LIVENESS_TTL_SECONDS` (30). If Zetaris is down (timeout, connection error, 5xx or a dead-engine reply, see Quirks) the run sends nothing more to Zetaris and serves every read from the offline sample, traced `degraded`, instead of waiting on each query's timeouts; any other refusal (auth, an unsupported statement) is `inconclusive` and the run goes ahead live. One `liveness` trace line per run (`cached: true` when reused); `GET /health` `zetaris` shows the last result and the cached companyfacts tables. Not yet verified against a real dead driver (the triage's experiment E5).

**Warm on start.** When the API starts in live mode (`SAMPLE_MODE=false`) with `ZETARIS_REST_URL` set, it runs the same `warm` in a background daemon thread (`ZETARIS_WARM_ON_START`, default `true`; sample mode ignores it). Startup never waits for it and a failure never stops the API; `GET /health` reports it as `zetaris_cache`: `state` `off` (with `reason`), `warming` (`done` of `total`), `warm`, `partial` or `failed` (with `error`). Its trace lines go to `logs/trace-warm-<UTC timestamp>.jsonl`. A run that starts while the warm is still going may still hit a cold table.

**First-query timeout.** A live query on a registered table that is not cached refetches the SEC response inside the query. If that passes `SOURCE_TIMEOUT_SECONDS` (20 s) on every retry, the call is an outage and degrades to the offline sample, as before; for a company outside the sample the run then ends at `evidence-frontier`. `warm` is the remedy, not a longer source timeout. Measured cold re-caches on 2026-10-24 (just after a driver restart): `ge_facts_raw` 22.8–23.9 s (over the source timeout), `gehc_facts_raw` 7.5–10.8 s, `gev_facts_raw` 5.7–10.1 s, other companies' companyfacts 2–18 s, a submissions table about 1–1.6 s, `sec_tickers_raw` 1.5 s; the warm with the earlier default (7 tables: the GE showcase and the ticker map) took 41.6 s; the current default (11) has not been timed live. After it, `SELECT count(*)` on `tiresias.ge_revenues` took 2.2 s and on `tiresias.ge_filings` 0.7 s.

**Discovery goes through Zetaris too** (ADR-0003). `bootstrap` registers the `sec_tickers` table and view; the live discovery adapter (`adapters/catalog.py`, `ZetarisDiscovery`) also registers them on first use. A REST table binds one URL, so reading one candidate's submissions means one `<ticker>_submissions_raw` table, registered on demand with the same template as bootstrap (CREATE + CACHE) and refused if an existing table of that name points at another CIK. The source scout's full-text searches work the same way: one `fts_<hash>_raw` table per search (at most two per scout run). These discovery objects are catalog reads, not evidence sources: they never count toward `MAX_NEW_SOURCES_PER_RUN`.

**Runtime registration.** An asked entity outside the showcase set is registered while the run is going (`onboarder.onboard_entity`: both raw tables, caches, the concept views and the filings view, behind the source gate); Loop B registers a discovered entity's companyfacts table and the views for the variable (`onboarder.onboard`). Both use these templates and count toward `MAX_NEW_SOURCES_PER_RUN`. Measured timings: [docs/measurements/live-any-company.md](../docs/measurements/live-any-company.md).

## Quirks

Found while building; each is handled in the code or the templates named here.

- **`companyfacts`, not `companyconcept`.** On 22 Oct 2026 SEC's `companyconcept` returned empty `units` for GE HealthCare while `companyfacts` had the data. The concept views therefore read `companyfacts` by struct path (`facts.us-gaap.<Concept>.units.USD`); exploding the whole facts map takes about 18 s, so nothing does that.
- **`sec_tickers` comes from `company_tickers_exchange.json`** (row arrays), not `company_tickers.json`: the latter is one object keyed `"0".."N"`, which Zetaris would infer as a struct with about 10,000 fields. The offline sample keeps a trimmed `company_tickers.json`; both carry CIK, ticker and name.
- **EDGAR full-text search** (`14_fulltext_table.sql`): the `forms` list must hold root forms only (`8-K`, not `8-K,8-K/A`; an `/A` form makes the search return nothing, and amendments match their root form anyway). A search with no hit makes Zetaris infer `hits.hits` as `array<string>`, so `40_fulltext_total.sql` runs first and `41_fulltext_hits.sql` only when the total is non-zero.
- **SEC fair access**: every SEC-fetching statement carries `SEC_USER_AGENT` (a contact email) and is paced at the catalog rate limit (at most 10 requests/s).
- **The cache does not survive a Zetaris restart** (see Apply): the first uncached query then refetches from SEC, measured at up to 24 s for GE's companyfacts against a 20 s source timeout (3M timed out three times on 2026-10-24 and degraded to the sample). Run `warm`, or let the API warm on a live start (BACKLOG B-20, closed).
- **Cached companyfacts tables use driver heap.** The bundle's driver has a 2 GB heap. Re-caching all 63 registered raw tables on 2026-10-24 ran it out of memory after about ten companyfacts tables (`java.lang.OutOfMemoryError: Java heap space`, then `stopping SparkContext`); from then on every statement failed in about 0.1 s with HTTP 400 (`Cannot call methods on a stopped SparkContext`, or a `FetchIterator.fetchNext()` NullPointerException) until `docker restart zetaris-driver-1`. Registrations survived the restart. Measured afterwards: each cached companyfacts table (one row of about 1,000 concepts) retained roughly 150 MB of heap outside Spark's storage pool, which neither eviction nor disk spill can reclaim, and caching one needed another 0.6–0.9 GB while it ran. Hence `ZETARIS_WARM_MAX_TABLES`, the halt after two failures in a row and the cache cap `ZETARIS_MAX_CACHED_FACTS` with `UNCACHE TABLE` of the least recently used table (see Apply; BACKLOG B-24).
- **A dead engine answers HTTP 400.** With a stopped SparkContext the server stays up (its healthcheck only opens a TCP port) and every statement fails in about 0.1 s with HTTP 400 and `Cannot call methods on a stopped SparkContext`, or a `NullPointerException` in `FetchIterator.fetchNext()`. A 400 is otherwise non-recoverable (bad SQL, auth, a refused object), so the adapter matches these two signatures (`DEAD_ENGINE_SIGNATURES` in `zetaris.py`, the only list) in the reply body and treats such a reply as an outage whatever its status: no retry, the call degrades to the sample (`degraded`), and the message says to restart the driver (`docker restart zetaris-driver-1`).
- **Discovery tables are never dropped** (`<ticker>_submissions_raw`, `fts_<hash>_raw`): bounded per run, but they accumulate across runs. Tracked as BACKLOG B-21.
