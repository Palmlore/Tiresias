## Building blocks (reuse these; don't rebuild them)
All under `services/agent/src/tiresias_agent/`. Each sponsor client takes an optional `tracer` and degrades instead of crashing (rule 8).

| Module | Use it for |
|---|---|
| `trace.py` | `Tracer(run_id=…, defaults={…}, sink=None)` → `.emit(agent=, action=, status=, **fields)` writes one JSONL line (stdout + `logs/trace-<run_id>.jsonl`); `defaults` are added to every line (Loop A sets `mode="sample"`/`"live"`, ADR-0007); `.span(...)` times a block. Statuses: `success`, `error`, `rejected`, `degraded`. Secret-like keys and Bearer tokens are redacted. `sink` (optional callable) also receives each redacted JSONL line; a failing sink is reported on stderr and never breaks the run. `NullTracer` for tests. **`phase(tracer, name, owner=, every=None)`** (context manager, any tracer): `orchestrator`/`phase_start`, an `orchestrator`/`heartbeat` line every `PHASE_HEARTBEAT_SECONDS` (default 5) while the block runs, then `orchestrator`/`phase_done` with `duration_ms` (status `error` if it raised); every line carries `phase` and `target_agent=owner`. See "Run phases (for UI)". Writes are serialised with a lock (heartbeats come from a thread). |
| `models.py` | Pydantic models for `contracts/openapi/agent.yaml`: `RunRequest`, `RunResult` (leads with `end_state`, `action`; carries `effect`, `information_need`, `why_tree` of `Link`s with `evidence: [EvidenceItem]`, `error`), `InformationNeed` + `EntityHint` (the Loop A → Loop B hand-off), `BranchRequest`, `RunStats`, `ErrorResponse`, … `Entity` is `ticker` / `cik` / `name` (name only used when neither of the others is given). Directory and scope shapes: `ScopeCheck` (`in_scope`, `reasons: [ScopeReason(type forecast/not-sec-registrant/not-in-sample, message, cue)]`, `alternatives: [Alternative(basis, entity, registered, checks, request)]`, `note`; on `RunResult.scope` only when the check stopped the run), `Suggestion` (kind, basis, question, metric, period, baseline, target, delta, checks, `request`), `EntityInfo` / `EntityList` / `SuggestionList`, `ExpectedWait`. |
| `config.py` | `settings` (env flags), `FIRST_RUN_SECONDS` (expected first-run wait per tier `sample` / `ready` / `searchable`, the measured 0–1 / 3–11 / 15–21 s from docs/measurements/live-any-company.md; re-measure before changing) and `LoopBudgets.from_env()`: `MAX_CAUSAL_DEPTH` (5), `MAX_BRANCHES_PER_LEVEL` (3), `MAX_RETRIES_PER_NODE` (1), `RUN_BUDGET_SECONDS` (600, shared by Loop A and B), `MAX_NEW_SOURCES_PER_RUN` (2, clamped 0..5, field `max_new_sources`), read at call time and clamped. |
| `orchestrator.py` | **Entry point: `run_investigation(request, **same kwargs as run_loop_a, discovery=None, zetaris_client=None, data_dir=None)` → `RunResult`**: Loop A, then `LoopB` when Loop A ends at `evidence-frontier` with an `InformationNeed` and a framed effect (otherwise a `loop_b` trace line says why it was skipped). **Loop A only:** `run_loop_a(request, *, source=None, tracer=None, gate=None, budgets=None, logs_dir=None)`. Neither raises for a bad case (structured `error`, or end state `budget`). **Both first resolve the asked entity** (`agents/entity_resolver.py`, phase `resolve_entity`), **then run the scope check** (`agents/scope.py`, phase `scope_check`: out of scope ends at `evidence-frontier` with `RunResult.scope` and nothing registered) and, live, register it if Zetaris lacks it (`onboarder.onboard_entity`, phase `register_entity`, behind the `source` gate, counted in `MAX_NEW_SOURCES_PER_RUN`, deadline = run start + `RUN_BUDGET_SECONDS`); an unresolvable/ambiguous entity, a denial, the cap or a failed registration ends at `evidence-frontier` with the reason, an invalid ticker/CIK is an `InvalidInput` error. Loop A: framer → (hypothesiser → analyst ⇄ critic [→ gate])* → gap analyst → reporter; stops at the first accepted causal link the asker's levers can act on, digs under the strongest breakdown otherwise. Loop B: source scout → onboarder [source gate] → `reconciler` (analyst + critic) → the same asker-relative stopping rule (`actionable` / `branched` / `external-driver`); an unresolvable hint, a gate denial, a failed registration or missing data keeps `evidence-frontier` with `Loop B: <why>` appended to `information_need.reason`; the source cap or the wall clock gives `budget`. CLI below. |
| `runs.py` | Run registry behind the HTTP API. `RunRegistry().start(request, run_id=None)` → `RunRecord` (runs in a daemon thread; raises `RunConflict` for a duplicate id, `RegistryBusy` beyond `MAX_CONCURRENT_RUNS`, default 4); keeps the last `RUNS_REGISTRY_SIZE` runs (default 50, oldest finished evicted) and up to `MAX_TRACE_LINES_PER_RUN` lines each (default 5000; the trace file keeps all). `RunRecord.wait(timeout)`, `.follow()` (replay then live lines, for SSE), `.summary()` (the `GET /runs/{id}` body). Adds `api` trace lines `run_accepted` / `run_finished` / `run_failed`. **`runs.execute(...)` is the one place the API calls the pipeline** (`orchestrator.run_investigation`). |
| `app.py` | FastAPI app. `GET /entities?q=&limit=&sample_mode=` and `GET /entities/{cik}/suggestions?role=&limit=&sample_mode=` (`entities.py`; 404 `EntityNotFound` / `EntityNotInSample`, 409 `EntityNotRegistered`, 422 bad CIK; `api` trace lines to `trace-<X-Run-Id>.jsonl`, else one `trace-api-YYYYMMDD.jsonl` per day). `POST /run` = `registry.start` + wait up to `RUN_BUDGET_SECONDS` + 30 s (`runs.wait_budget_seconds()`); `POST /runs` (202), `GET /runs/{id}`, `GET /runs/{id}/events` (SSE: `event: trace` per JSONL line, `: keepalive` every 15 s idle, one final `event: end`). Every error is the contract's `Error` shape via `error_response(...)`: 422 `ValidationError` (body, JSON or `X-Run-Id`), 404 `RunNotFound`, 409 `RunConflict`, 429 `TooManyRuns`, 500 (pipeline raised), 504 `RunTimeout`, 501 `NotImplemented`. `X-Run-Id` (`[A-Za-z0-9._-]{1,100}`) is honoured and echoed. CORS is off unless `CORS_ALLOW_ORIGINS` is set. |
| `entities.py` | Entity directory behind the two `GET /entities` endpoints. `list_entities(q, sample=, source=, discovery=callable, tracer=, limit=)` → `EntityList`: tier `ready` = registered (live: facts table + filings view + a supported metric view, names from `sec_tickers`; sample: the slice), tier `searchable` = live `sec_tickers` matches for `q` (ticker, CIK or name, 2+ characters) and partly registered entities matching it; each with `expected_first_run` from `FIRST_RUN_SECONDS`. Sample mode lists only the slice and says why in `note`; an outage serves the sample, `degraded: true`. `suggestions(cik, ...)` → `SuggestionList` for a ready entity (`suggester.suggest`), else `DirectoryError(status, type, message)`. |
| `agents/suggester.py` | Questions from an entity's own data. `suggest(entity, source, tracer=, asker=, limit=, sample_mode=)` → `SuggestResult(suggestions, considered, rejected)`: per `knowledge.SUGGESTED_METRICS` (Revenues, NetIncomeLoss), annual facts only: **restatements** (first time two consecutive annual filings disagree on a fiscal year; newest restating filing first, at most `MAX_RESTATEMENTS`), the **largest changes** (`CHANGES_PER_METRIC` by absolute delta) and the **lowest / highest value** (only if it is the extreme of every reported annual value and the year frames). Every candidate is a `RunRequest` **validated by the framer itself** (kind as intended, relative change ≥ `MIN_RELATIVE_CHANGE` 1%); neutral wording (differ / rise / fall / was). `latest_change(entity, source, metric, asker=)` → the most recent validated change (the scope check's past-period alternative). `CachingSource` memoises the series. |
| `agents/scope.py` | Scope check after `resolve_entity`, before Loop A. `check(request, resolution, sample=, source=, discovery=callable, tracer=, today=None)` → `ScopeCheck`. Reasons: `forecast` (`forward_cue(question)`: strong cues "what if", "will", "going to", "suppose", "what/how would" or "would … if" without a "have" within three words, always; weak cues "forecast", "predict", "projection", "outlook", "expect … to", "next year/quarter" only when the question is not framed as explaining the past, "Why did …"; or a period ending after today), `not-sec-registrant` (live `EntityNotFound` with zero `sec_tickers` rows, never when degraded), `not-in-sample` (sample). Up to `MAX_ALTERNATIVES` (3) runnable `RunRequest`s: registrants **named in the question** (capitalised phrases, `name_phrases`, each matching exactly one CIK in `sec_tickers`), the **same entity, past period**, **same SIC peers** among registered entities (`discovery.registrant` → `sic`, at most `MAX_PEER_PROBES`, cached). Registered → `suggester.latest_change`; unregistered (live) → the fiscal year between its two latest 10-K report dates, `registered: false` (the run registers it). |
| `agents/framer.py` | `frame(request, source, tracer)` → `Frame`: a like-for-like effect. `restatement` when `compare.filing_a/filing_b` are `"<form> filed YYYY-MM-DD"` (same period, two filings), else `change` (period vs prior period, both from the first annual filing reporting the period). Raises `FrameFailure` (metric not in sources → evidence-frontier) or `LoopError`. |
| `agents/hypothesiser.py` | Rule-based (ADR-0007). `propose(frame, parent, path_variables, max_branches=, tracer=, exclude=)` → `Candidate`s from generic rules in `agents/knowledge.py`: hierarchy children, event concepts (goodwill impairment), 8-K items (2.01 disposal, 4.02 non-reliance / 10-K/A), concept switch, restated comparative. No cycles, capped. |
| `agents/analyst.py` | `measure(candidate, frame, source, attempt=, scope=, tracer=)` → `Measurement`: queries only through `EvidenceSource`, keeps SQL + filter + rows per query, computes the candidate's effect and the counterfactual (intervention re-query on the returned rows). Scopes: `broad` → `window` → `relaxed` (set by the critic). |
| `agents/critic.py` | Pure rules over a `Measurement`: `judge(candidate, m, frame, retries_left=)` → `Verdict` (`accept` / `prune` / `retry` / `frontier`, label, evidence status, share vs the root effect); `apply_gate(verdict, choice)`. Thresholds in `agents/common.py` (`MOST_OF_EFFECT`, `MIN_SHARE`, …). |
| `agents/gap_analyst.py` | `for_candidate(frame, node, tracer)` / `for_variable(...)` / `for_breakdown(frame, ruled_out, tracer)` (every tested candidate was a ruled-out accounting/filing event, `knowledge.EVENT_RULES`: says what was ruled out and asks for `<metric> by segment or product`, relation `same entity, breakdown`; Loop B is skipped for it) → `InformationNeed` (variable + aliases, entity hint from the run's own evidence, period, join key, expected magnitude, the intervention test to run). **Loop B consumes this.** |
| `agents/entity_resolver.py` | Before Loop A. `resolve(request, source=, sample=, tracer=, discovery=callable, views=callable)` → `Resolution(entity, registered, reason, error_type, evidence, candidates)`. Registered entities first (CIK, ticker, then name; live also needs the filings view and a metric view). Sample: anything else is `EntityNotInSample`, with a reason that lists the slice's entities and how to run live. Live: `discovery.lookup(tickers=, ciks=)` or `.search(name)` over the Zetaris `sec_tickers` view; one CIK resolves it, none is `EntityNotFound`, several (or a ticker/CIK that disagree) is `EntityAmbiguous`. Object names use `zetaris.object_ticker` (`BRK-B` → `brkb`). |
| `agents/source_scout.py` | Loop B. `resolve(need, discovery=, tracer=)` → `ScoutResult(entity, template, reason, evidence, candidates)`. Rule-driven, catalog-only: the hint must name an 8-K 2.01 filing; the source row comes from `discovery.lookup(...)` and candidates from `discovery.brand(words)`: `sec_tickers` rows carrying the source's brand (newest CIK first, ≤ `MAX_CANDIDATES`); a candidate qualifies if its `sec_submissions` show it became a separate registrant at that disposal (registrant by the date, no 10-K before it, its own 8-K within `SEPARATION_WINDOW_DAYS`, item 5.01 ranks higher); exactly one best match or it refuses. `assess()` and `pick_template()` (registrable XBRL template with the fewest registrations: `sec_companyfacts`) are pure. |
| `agents/onboarder.py` | Loop B. `onboard(scout, need, gate=, registry=, cap=, sample=, tracer=, client=None, data_dir=None)` → `Registration(status registered/degraded/denied/capped/failed, mode zetaris/sample)`: cap check → dry run (`bootstrap_plan(..., tables=("facts",))`, nothing executed) → `source` gate (options `register`/`deny`, proposal `register`) → live `bootstrap(...)` one statement at a time + view refresh, or a **sample-mode registration** (traced `registration: "sample"`, Zetaris not called). Outage → degraded to the sample; non-recoverable → failed. `Registry(source, asked, onboarded=())` is what the Loop B analyst queries: it raises `SourceError` for any entity not registered in this run; `onboarded` seeds the cap count (the asked entity, if this run registered it). **`onboard_entity(entity, metric=, gate=, used=, cap=, tracer=, client=, deadline=, clock=)`**: the asked entity, live only: cap → dry run → `source` gate (`context.scope: "asked_entity"`) → `bootstrap` of both raw tables, their caches, the concept views (`CONCEPT_SLUGS` + the metric and its aliases) and the filings view; no sample fallback (the slice only holds the showcase entities). Both forward `deadline` to `bootstrap`. |
| `agents/reconciler.py` | Loop B analyst + critic. `measure(frame, need, entity, source, node_id=, tracer=)` → `Reconciliation` (the entity's first annual value of the metric for the period, `restated + disposed` counterfactual, residual amount); `judge(frame, r)` → (`Verdict`, signed residual share): accept `evidenced` if it explains ≥ `MOST_OF_EFFECT` and the add-back is within `RECONCILE_TOLERANCE` (5%) of the original, escalate when it over-explains beyond tolerance, prune below `MIN_SHARE`, frontier when the data or a restatement frame is missing. ## Run phases (for UI)
Every slow phase is bracketed by trace lines on the SSE stream (`GET /runs/{id}/events`): `agent: "orchestrator"`, `action: "phase_start"` / `"phase_done"`, field `phase` (below), `target_agent` (the agent doing the work), `duration_ms` and `status` on `phase_done` (plus `outcome` / `end_state` where useful); while a phase runs, `action: "heartbeat"` with the same `phase` and `elapsed_ms` every `PHASE_HEARTBEAT_SECONDS` (default 5), so no wait is silent for more than ~5 s. Nested phases close before their parent. Measured live on 2026-10-23 ([docs/measurements/live-any-company.md](docs/measurements/live-any-company.md)); sample mode runs every phase in milliseconds.

| `phase` | Owner (`target_agent`) | When | Typical live duration |
|---|---|---|---|
| `resolve_entity` | `entity_resolver` | every run | 0.1–0.6 s |
| `scope_check` | `scope` | every run | ~1 ms in scope; out of scope (live, 2026-10-23) 0.4 s, or 1.8 s when an alternative's submissions discovery table is created first |
| `register_entity` | `onboarder` | live, asked entity not in Zetaris yet (cold) | 11.8–15.6 s (one companyfacts `CACHE TABLE`, 7–12 s, is most of it); absent when warm |

## How work lands (from 23 Oct 2026)
- **Every change goes through a pull request**, one task per branch (`feat/<short-name>`), file-disjoint from other open PRs so they can run in parallel. Process and housekeeping commits may go straight to `main`.
- The PR body follows [.github/pull_request_template.md](.github/pull_request_template.md): an `## ACCEPTANCE CRITERIA` section of `[C]` / `FALSIFIED-BY:` / `VERIFIER:` entries. Make each criterion testable by a named test or command.
- Each PR is reviewed by **DuelLoop** (`~/Repos/duelloop`, outside this repo): Codex as adversarial reviewer, Claude Code as worker, up to 5 rounds (`--rounds 5`). The coordinating session launches it backgrounded (`duelloop go --pr N --worker claude --reviewer codex --repo <worktree>`); run records live in `~/.duelloop/runs/`, never in this repo. The local `verdict.json` is the source of truth, not the PR label.
- On `MERGE_PERMITTED` the coordinator re-runs every verifier itself and merges (squash) only if they pass: `uv` panics inside the reviewer's macOS sandbox, so the reviewer probes behaviour but often cannot run the suite. Escalations go to the human.
- A PR that adds a feature, module, CLI or observability also updates **AGENTS.md** (Building blocks, Commands, gotchas) and, if a judge would see the change, **README**, in the same PR and as an acceptance criterion. Later tasks build on what is documented there.
- Docs-only PRs (status, checklist, README) go through DuelLoop too. Their criteria test **accuracy** (every claim matches the code and git history; nothing is marked working that a judge can't run) and **logical consistency** (CHECKLIST, STATUS, README, metadata.json and AGENTS.md agree with each other).
- Real findings that are out of scope are **deferred** to [BACKLOG.md](BACKLOG.md) in the same commit, with all four fields.
- Worker and reviewer rounds: commit to the PR branch only; don't push, open, approve or merge PRs.
- Parallel PRs don't edit `docs/CHECKLIST.md`, `docs/STATUS.md` or `metadata.json` (they would conflict); the coordinator updates them right after each merge.

## Rules (non-negotiable)
1. **No hardcoded or replayed outputs, no hand-written traces.** Judges test with their own inputs. Sample mode runs real logic on cached data.
2. **Every agent action writes a JSONL trace line** (schema: `docs/architecture.md#tracing`), propagating `X-Run-Id`.
3. **Secrets only in `.env`** (gitignored). Never print keys; mask them in logs and screenshots.
4. **Honest status.** `metadata.json` and the checklist say `working` or `done` only when a judge can see it run. Update `docs/CHECKLIST.md`, `docs/STATUS.md` and `metadata.json` in the same commit as the work.
5. **Destructive operations run alone.** Any `rm`, overwrite, `git reset`, `docker compose down -v` or memory purge goes in its own command with a one-line reason, never inside a larger script.
6. **Don't edit vendored code** (`services/cognition/engine/`). Wrap it.
7. Bound everything: timeouts on external calls, capped loops (`MAX_CAUSAL_DEPTH`, `MAX_BRANCHES_PER_LEVEL`, `MAX_NEW_SOURCES_PER_RUN`).
8. Sponsor calls go behind adapters with a fallback, so an outage degrades the run instead of crashing it.

## Known gotchas
- SEC `companyconcept` returned **empty** `units` for GE HealthCare on 22 Oct while `companyfacts` had the data. Use `companyfacts` with struct-path views (`facts.us-gaap.<Concept>.units.USD`). Don't explode the whole map (18 s).
- The same concept can appear under different names (`Revenues` vs `RevenueFromContractWithCustomerExcludingAssessedTax`).
- H-MEM recall threshold is 0.25 (`RECALL_THRESHOLD`). To show the critic rejecting a misapplied lesson, recall with a broad query.
- Node runs TypeScript with `--experimental-transform-types` (the vendored engine uses parameter properties).
- SEC requires `User-Agent` with a contact email (`SEC_USER_AGENT`), at ≤10 requests/s.
- Zetaris `CACHE TABLE` is lost when Zetaris restarts: re-run `bootstrap`, or the first uncached query takes ~15 s (the source timeout is 20 s).
- A concept view that fails with `FIELD_NOT_FOUND` means SEC has no such concept for that entity; `bootstrap` reports it `absent` and the adapter skips it.
- The agent image is built from the **repo root** (`compose.yaml`: `context: .`, `dockerfile: services/agent/Dockerfile`) and mirrors the repo under `/app` (`/app/services/agent`, `/app/data/sample`, `/app/zetaris/sql`, `/app/catalog`, `/app/input_examples`), so the package's repo-relative defaults resolve; `SAMPLE_DATA_DIR`, `ZETARIS_SQL_DIR` and `LOGS_DIR=/app/logs` are also set. The root `.dockerignore` is an **allow-list**: a new directory the image needs must be added there and to the Dockerfile (`tests/test_packaging.py` checks both). The `RunResult.trace_file` path is the container path; on the host it is `logs/` (mounted).
- The run registry is in memory and per process: `GET /runs/{id}` forgets runs after a restart or once `RUNS_REGISTRY_SIZE` newer runs finished (trace files stay in `logs/`). A run that outlives `POST /run`'s wait (504) keeps running in its thread; poll `GET /runs/{id}`.
- `POST /run` returns 200 for any run that ended (including `RunResult.status: "error"` from a controlled `LoopError`); 500 only when the pipeline itself raised.
- The Zetaris admin defaults to `admin@zetaris.com` (change the password in the UI).
- Loop A only queries the **asked entity** (its concept series and filings). Evidence that lives in another entity (e.g. a spun-off business) is an `InformationNeed` for Loop B, even if that entity happens to be in `data/sample/` or registered in Zetaris.
- A restatement of a closed period is caused by an event **after the period ends and no later than the restating filing** (`Frame.window()`); a change is caused during the period. The critic's temporal test uses this window.
- Shares are measured against the **root** effect and capped at 100%; a candidate that over-explains (offsetting factors) goes through the critic-escalation gate.
- Loop B's sample-mode "registration" is not a Zetaris call: it checks that `data/sample/<ticker>_companyfacts.json` holds that CIK and lets the `Registry` serve it; the trace says `registration: "sample"`. In live mode it runs `bootstrap` for the one entity (facts table + concept views only).
- The source scout's candidate pre-filter is the brand (first word of the ticker-map title equals the source's ticker or first title word). A disposal to an existing company, or into a registrant with a new brand, is refused and stays `evidence-frontier` (BACKLOG B-5).
- A Loop B residual is **signed**: case 02's add-back over-explains (negative residual). Shares stay capped at 100%.
- In live mode **every read goes through Zetaris**, discovery included: nothing in `services/agent/src` names an SEC endpoint or opens HTTP except the three sponsor adapters (`tests/test_any_company.py` guards it). SEC URLs live only in `catalog/sources.yaml` and `zetaris/sql/`; Zetaris fetches them with `SEC_USER_AGENT`. `scripts/fetch_sample.py` is offline tooling that rebuilds `data/sample/`, not a runtime path.
- `sec_tickers` is registered from `company_tickers_exchange.json` (row arrays), not `company_tickers.json`: the latter is one object keyed `"0".."N"`, which Zetaris would infer as a struct with ~10k fields. The sample keeps the trimmed `company_tickers.json`; both carry CIK, ticker and name.
- Registration status lines: the Zetaris client traces `bootstrap:database` / `container` / an existing table as `status: error` ("already exists") before `bootstrap` classifies it as `exists`; read the `onboarder` `register` line (or `phase_done`) for the outcome (BACKLOG B-9).
- **Cold vs warm (live):** the first run for a company Zetaris has never seen registers it (`register_entity`, 12–16 s, mostly the companyfacts `CACHE TABLE` download) and is 15–21 s end to end; the next run is 3–11 s. Registrations persist in Zetaris; the cache does not survive a Zetaris restart (the first query then refetches). Measured in `docs/measurements/live-any-company.md`.
- Discovery tables pile up: each scout run may register up to `MAX_CANDIDATES` `<ticker>_submissions_raw` tables (CREATE + CACHE, ~0.6–1.3 s each the first time). They are reused by later runs and never dropped (bootstrap never drops).
- An entity asked about in sample mode that is not in `data/sample/` ends in milliseconds at `evidence-frontier` (`EntityNotInSample`); the reason lists the slice and how to run live.
- **Out of scope keeps the six end states** (ADR-0004): a forecast/what-if or a non-SEC company ends at `evidence-frontier` with `status: partial`, `RunResult.scope` (reasons + alternatives) and no effect; an unresolved entity also keeps its `information_need` (as before), a forecast about a resolved entity has none. Nothing is registered by the check; reading an alternative's submissions may add a discovery table (`<ticker>_submissions_raw`, not counted in `MAX_NEW_SOURCES_PER_RUN`).
- A company outside SEC has no SIC code in our data, so without a model the scope check can only offer SEC registrants **named in the question**; peers come from **registered** entities only (no SIC index in the catalog). A Nightshift model could propose the industry later: the model proposes, the agent validates (BACKLOG B-12).
- `GET /entities/{cik}/suggestions` needs a **registered** entity (409 `EntityNotRegistered` otherwise: run any question about it first, BACKLOG B-13). Suggestions are derived from the data, so the demo controls which ones it features; the engine never tilts them.
- When every candidate Loop A tested was an accounting or filing event and each was ruled out (a plain year-on-year rise, no disposal or restatement), the frontier says so and asks for a segment/product breakdown; SEC company facts have no segment data, so Loop B is skipped (`loop_b` line `rejected`).
- The CLI resolves a relative request path against the cwd, then the repo root, and writes traces to `<repo>/logs/` unless `LOGS_DIR` or `--logs-dir` is set.
