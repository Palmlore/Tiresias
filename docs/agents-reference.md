# Agent reference: building blocks, run phases, external services

The detail behind [AGENTS.md](../AGENTS.md). Read the section a task needs; nothing here is required reading at the start of a session. A PR that adds or changes a module, a phase or an external call updates this file in the same change.

## Building blocks (reuse these; don't rebuild them)
All under `services/agent/src/tiresias_agent/`. Each sponsor client takes an optional `tracer` and degrades instead of crashing (rule 8).

| Module | Use it for |
|---|---|
| `trace.py` | `Tracer(run_id=…, defaults={…}, sink=None)` → `.emit(agent=, action=, status=, **fields)` writes one JSONL line (stdout + `logs/trace-<run_id>.jsonl`); `defaults` are added to every line (Loop A sets `mode="sample"`/`"live"`, ADR-0007); `.span(...)` times a block. Statuses: `success`, `error`, `rejected`, `degraded`. Secret-like keys and Bearer tokens are redacted, and any value of a secret-looking environment variable (name with token/key/password/secret/authorization, 8+ characters: `secret_env_values()`, `mask_secret_values(text)`) is masked on every line, wherever it is echoed (a question, a note). `sink` (optional callable) also receives each redacted JSONL line; a failing sink is reported on stderr and never breaks the run. `NullTracer` for tests. **`phase(tracer, name, owner=, every=None)`** (context manager, any tracer): `orchestrator`/`phase_start`, an `orchestrator`/`heartbeat` line every `PHASE_HEARTBEAT_SECONDS` (default 5) while the block runs, then `orchestrator`/`phase_done` with `duration_ms` (status `error` if it raised); every line carries `phase` and `target_agent=owner`. See "Run phases (for UI)". Writes are serialised with a lock (heartbeats come from a thread). |
| `models.py` | Pydantic models for `contracts/openapi/agent.yaml`: `RunRequest`, `RunResult` (leads with `end_state`, `action`; carries `effect`, `information_need`, `why_tree` of `Link`s with `evidence: [EvidenceItem]`, `error`), `InformationNeed` + `EntityHint` (the Loop A → Loop B hand-off), `BranchRequest`, `RunStats`, `ErrorResponse`, … `Entity` is `ticker` / `cik` / `name` (name only used when neither of the others is given). Investigation depth (ADR-0011): `RunOptions.depth` (`Depth` = `quick` (default) / `thorough` / `deep`; `RunOptions.model_lanes` `auto`/`on`/`off` is deprecated: `on` = `deep`, `off` = `quick`, ignored when `depth` is set), `RunResult.depth` and the `POST /runs` 202 body's `depth` (`RunDepth`: `requested`, `requested_by` options.depth/options.model_lanes/MODEL_LANES/default, `effective`, `lanes`, `degraded`, `note`, `expected_wait`), `EntityInfo.expected_first_run_by_depth` (`DepthWaits`: `quick`/`thorough`/`deep` → `ExpectedWait`; `expected_first_run` stays the quick wait). Model lanes (ADR-0010): `Link.proposed_by` (`rules`/`model`) and `Link.model_opinion` (`ModelOpinion`: lane, requested/routed model, provider, receipt id, decision, label, rationale, `grounded`, `agrees`, `rule_decision`, `gate_choice`), `RunResult.action_source` (`template`/`model`) and `action_template`. Directory and scope shapes: `ScopeCheck` (`in_scope`, `reasons: [ScopeReason(type forecast/not-sec-registrant/not-in-sample, message, cue)]`, `alternatives: [Alternative(basis, entity, registered, checks, request)]`, `note`; on `RunResult.scope` only when the check stopped the run), `Suggestion` (kind, basis, question, metric, period, baseline, target, delta, checks, `request`), `EntityInfo` / `EntityList` / `SuggestionList`, `ExpectedWait`. |
| `config.py` | `settings` (env flags), `FIRST_RUN_SECONDS` (expected first-run wait per tier `sample` / `ready` / `searchable`, the measured 0–1 / 3–11 / 15–21 s from docs/measurements/live-any-company.md; re-measure before changing) and `LoopBudgets.from_env()`: `MAX_CAUSAL_DEPTH` (5), `MAX_BRANCHES_PER_LEVEL` (3), `MAX_RETRIES_PER_NODE` (1), `RUN_BUDGET_SECONDS` (600, shared by Loop A and B), `MAX_NEW_SOURCES_PER_RUN` (2, clamped 0..5, field `max_new_sources`), `MAX_MODEL_CALLS_PER_RUN` (12, clamped 0..50, field `max_model_calls`), read at call time and clamped; `model_lanes_mode(env=None)`: `MODEL_LANES` = `auto` (default: the request's depth decides; anything invalid is `auto`) / `on` (`deep` when the request names no depth) / `off` (`quick` at every depth); `DEPTHS` (`quick`, `thorough`, `deep`), `DEFAULT_DEPTH` (`quick`), `MODEL_SECONDS` (model time a depth adds live: 0 / 91–94 / 142–145 s, measured on case 01 on 2026-10-24, ADR-0011; re-measure before changing) and `expected_seconds(tier, depth, sample)` → `(min, max, basis)` = `FIRST_RUN_SECONDS[tier]` + `MODEL_SECONDS[depth]` (`tier=None`: warm or cold, 3–21 s; sample: milliseconds at every depth); `max_over_explained(env=None)`: `MAX_OVER_EXPLAINED` (default `MAX_OVER_EXPLAINED_DEFAULT` = 1.5, i.e. 150% of the root effect, clamped 1.05..10.0, read at call time), the Loop B critic's bound on an over-explaining add-back; `max_cached_facts(env=None)`: `ZETARIS_MAX_CACHED_FACTS` (default 5, clamped 1..50, read at call time), the companyfacts tables a process keeps cached in Zetaris; `LivenessSettings.from_env()`: `ZETARIS_LIVENESS_TTL_SECONDS` (30, 0..600) and `ZETARIS_LIVENESS_TIMEOUT_SECONDS` (3, 0.5..30). |
| `orchestrator.py` | **Entry point: `run_investigation(request, **same kwargs as run_loop_a, discovery=None, zetaris_client=None, data_dir=None, memory_client=None)` → `RunResult`** (both also take `lanes=` a `model_lanes.ModelLanes`, built from the request's depth and env when omitted; see `agents/model_lanes.py`; `depth_plan(request, switch=None, unavailable=None)` → `RunDepth`, the depth and expected wait before a run (the 202 body) and on `RunResult.depth`): Loop A, then `LoopB` when Loop A ends at `evidence-frontier` with an `InformationNeed` and a framed effect (otherwise a `loop_b` trace line says why it was skipped). **Loop A only:** `run_loop_a(request, *, source=None, tracer=None, gate=None, budgets=None, logs_dir=None)`. Neither raises for a bad case (structured `error`, or end state `budget`). **Both first resolve the asked entity** (`agents/entity_resolver.py`, phase `resolve_entity`), **then run the scope check** (`agents/scope.py`, phase `scope_check`: out of scope ends at `evidence-frontier` with `RunResult.scope` and nothing registered) and, live, register it if Zetaris lacks it (`onboarder.onboard_entity`, phase `register_entity`, behind the `source` gate, counted in `MAX_NEW_SOURCES_PER_RUN`, deadline = run start + `RUN_BUDGET_SECONDS`); an unresolvable/ambiguous entity, a denial, the cap or a failed registration ends at `evidence-frontier` with the reason, an invalid ticker/CIK is an `InvalidInput` error. Loop A: framer → (hypothesiser → analyst ⇄ critic [→ gate])* → gap analyst → reporter; stops at the first accepted causal link the asker's levers can act on, digs under the strongest breakdown otherwise. Loop B: source scout → onboarder [source gate] → `reconciler` (analyst + critic) → the same asker-relative stopping rule (`actionable` / `branched` / `external-driver`); an unresolvable hint, a gate denial, a failed registration or missing data keeps `evidence-frontier` with `Loop B: <why>` appended to `information_need.reason`; the source cap or the wall clock gives `budget`. **Live only (B-24):** before anything else the run checks Zetaris (`adapters.zetaris.check_liveness`, one `liveness` line; down means the run's client sends nothing more and every read is served from the sample, traced `degraded`); it `pin`s the asked entity's companyfacts table and, after the scout, the Loop B counterparty's in `FACTS_CACHE`, so the cache cap never evicts them while the run goes on; after the `scout` phase it releases the discovery tables the run cached except the asked entity's and the chosen counterparty's (`release_cache`), and at the end of the run releases what is left (except the asked entity's) and unpins. Sample mode does none of this. **Memory (`run_investigation` only, `agents/memory.py`):** the run's `MemoryRun` comes from `RunOptions.memory`, else `MEMORY_MODE` (`memory_client` defaults to a `CognitionClient` on `COGNITION_URL`); warm, phase `recall` runs after `frame`, Loop A passes `memory.preferences()` to the hypothesiser and `memory.observe(node, frame)` after each tested node (a conclusive lesson stops the level: the rest are `memory.skip`ped; the why-tree is appended in the rules' node order), Loop B observes the reconcile node; if a skip happened and the run ends outside `actionable`/`branched`/`external-driver`, `memory.fall_back` and Loop A (and B) run once more from the frame with every candidate, counters carried over; phase `remember` then sends `helpful` feedback and the write-back. `RunResult.memory` reports it; `stats.gate_decisions` includes the memory gate. `run_loop_a` has no memory (`RunResult.memory` null). CLI below (`--memory warm|cold`, `--interactive`: answer each gate on stdin through `stdin_ask`, an empty line takes the proposal, end of input leaves it to the policy). Both entry points take `ask=` (an interactive gate channel, used when `hitl_mode` is `interactive` and no `gate` is given). |
| `runs.py` | Run registry behind the HTTP API. `RunRegistry().start(request, run_id=None)` → `RunRecord` (runs in a daemon thread; raises `RunConflict` for a duplicate id, `RegistryBusy` beyond `MAX_CONCURRENT_RUNS`, default 4); keeps the last `RUNS_REGISTRY_SIZE` runs (default 50, oldest finished evicted) and up to `MAX_TRACE_LINES_PER_RUN` lines each (default 5000; the trace file keeps all). `RunRecord.wait(timeout)`, `.follow()` (replay then live lines, for SSE), `.summary()` (the `GET /runs/{id}` body, with `hitl_mode` and `waiting_gate`: the pending `GateWaiting` or null). Adds `api` trace lines `run_accepted` / `run_finished` / `run_failed`. **`runs.execute(...)` is the one place the API calls the pipeline** (`orchestrator.run_investigation`, which takes `ask=`). `runs.hitl_mode(request)` = `RunOptions.hitl_mode`, else `HITL_MODE`; when it is `interactive`, the run gets `RunRecord.gates = GateChannel(...)` (deadline = start + `RUN_BUDGET_SECONDS`) and the runner is called with `ask=record.gates.ask`; otherwise the runner is called exactly as before. |
| `app.py` | FastAPI app. `GET /entities?q=&limit=&sample_mode=` and `GET /entities/{cik}/suggestions?role=&limit=&sample_mode=` (`entities.py`; 404 `EntityNotFound` / `EntityNotInSample`, 409 `EntityNotRegistered`, 422 bad CIK; `api` trace lines to `trace-<X-Run-Id>.jsonl`, else one `trace-api-YYYYMMDD.jsonl` per day). `POST /run` = `registry.start` + wait up to `RUN_BUDGET_SECONDS` + 30 s (`runs.wait_budget_seconds()`); `POST /runs` (202 `{run_id, status, events, depth}`, `depth` = `orchestrator.depth_plan`: the depth and its expected wait before the run starts), `GET /runs/{id}`, `GET /runs/{id}/events` (SSE: `event: trace` per JSONL line, `: keepalive` every 15 s idle, one final `event: end`; the gate `waiting` / `answered` / `expired` / `decide` lines arrive on it, so a UI needs no polling). **Interactive gates:** `GET /runs/{id}/gates` → `GateList {run_id, hitl_mode, waiting_gate, gates}` (empty for auto/scripted runs); `POST /runs/{id}/gates/{gate_id}` with `GateAnswer {choice, note?, auto?}` → 200 the answered `GateWaiting` (`decided_by` `human`, or `ui-auto` when `auto: true`: a UI's countdown applied the proposal, and only the proposal may be applied so, else 422); `POST /runs/{id}/gates/{gate_id}/hold` with optional `GateHold {note?}` → 200 the `GateWaiting` with status `held` (idempotent; 404 / 409 like an answer): the gate waits for the user's answer, bounded only by the run budget; 404 `RunNotFound` / `GateNotFound` (also for a run without interactive gates), 409 `GateAlreadyAnswered` / `GateExpired`, 422 `ValidationError` (a choice not in `options`, or a bad body). Every error is the contract's `Error` shape via `error_response(...)`: 422 `ValidationError` (body, JSON or `X-Run-Id`), 404 `RunNotFound`, 409 `RunConflict`, 429 `TooManyRuns`, 500 (pipeline raised), 504 `RunTimeout`, 501 `NotImplemented`. `POST /memory/purge?namespace=` (optional body `PurgeRequest {namespace, requested_by}`) calls `CognitionClient.purge` through `app.memory_client(run_id, tracer)` (tests replace it) and returns `PurgeResult {status: purged, purged, namespace, requested_by}` with the count cognition confirmed; unreachable cognition is 503 `MemoryUnavailable` (recoverable), a refused or malformed reply 502 `MemoryError`, never a claimed purge; one `api` / `memory_purge` trace line either way (to `trace-<X-Run-Id>.jsonl`, else `trace-api-YYYYMMDD.jsonl`). `X-Run-Id` (`[A-Za-z0-9._-]{1,100}`) is honoured and echoed. CORS is off unless `CORS_ALLOW_ORIGINS` is set. `GET /health` never waits on a dependency: `zetaris_cache` (the warm on start) and `zetaris` (`zetaris_health()`: the last liveness probe `state` `off` in sample mode / `not-checked` / `alive` / `down` / `inconclusive`, with `reason`, `checked_at`, `duration_ms`, plus `cached_facts`, `max_cached_facts`, `pinned`; contract `ZetarisHealth`). `PUBLIC_DEMO=true` (the hosted demo; `public_demo()`, read per request, reported by `/health` as `public_demo`): a run or directory call asking for live mode (or a server with `SAMPLE_MODE=false`) gets 403 `LiveModeDisabled`, `POST /memory/purge` gets 403 `PurgeDisabled` without calling cognition (`tests/test_public_demo.py`). |
| `web/` (`index.html`, `app.js`, `story.js`, `app.css`, brand SVGs, `phase-*.svg` and `empty-investigation.svg` copied from `assets/`) | Web UI, static files mounted by `app.py` at `/ui` (`GET /` redirects there; `WEB_DIR`). **Two views of one run.** The default **Story** view (`story.js`) reads the run as a conversation: You ask, Tiresias proposes (one message per why-tree level), the Sphinx gives that level's verdicts (with Nemotron's second opinion inline when a `second_opinion`/`reject` line exists, live only), decisions follow (an automatic one as one line with "why ▸"; with "Pause at each decision (5 s to take over)" first the Sphinx asks on the user's behalf (`sphinxAsks(gateLine)`, one plain question per gate) with **Proceed** and **Take over** and a 5 s countdown (`promptGate(gateLine, deps)`, `PROMPT_SECONDS`): at 0, or on Proceed, the UI posts the recommended choice to `POST /runs/{id}/gates/{gate_id}` with note `proceeded automatically after 5 s (UI)` or `proceed (UI)`; the countdown's POST carries `auto: true` (recorded as `decided_by: "ui-auto"`), and the note on the `gate`/`answered` line also says which kind it was; **Take over** first posts `POST /runs/{id}/gates/{gate_id}/hold` (`deps.hold`; a 409 shows what applied), then shows the STAR card with no countdown, "Paused · your call" and the recommended button nudged (`.btn.nudge`); a `gate`/`budget` line reads "Paused until the run budget ran out; Three example bubbles post `input_examples/04`, `01` and `03` verbatim. Run settings map to `options.hitl_mode` (default `auto`), `options.memory`, `options.depth` (live mode only) and `options.sample_mode` (only offered when the server runs live). |
| `entities.py` | Entity directory behind the two `GET /entities` endpoints. `list_entities(q, sample=, source=, discovery=callable, tracer=, limit=)` → `EntityList`: tier `ready` = registered (live: facts table + filings view + a supported metric view, names from `sec_tickers`; sample: the slice), tier `searchable` = live `sec_tickers` matches for `q` (ticker, CIK or name, 2+ characters) and partly registered entities matching it; each with `expected_first_run` from `FIRST_RUN_SECONDS` (quick) and `expected_first_run_by_depth` (`expected_by_depth(tier, sample)`, via `config.expected_seconds`). Sample mode lists only the slice and says why in `note`; an outage serves the sample, `degraded: true`. `suggestions(cik, ...)` → `SuggestionList` for a ready entity (`suggester.suggest`), else `DirectoryError(status, type, message)`. |
| `agents/suggester.py` | Questions from an entity's own data. `suggest(entity, source, tracer=, asker=, limit=, sample_mode=)` → `SuggestResult(suggestions, considered, rejected)`: per `knowledge.SUGGESTED_METRICS` (Revenues, NetIncomeLoss), annual facts only: **restatements** (first time two consecutive annual filings disagree on a fiscal year; newest restating filing first, at most `MAX_RESTATEMENTS`), the **largest changes** (`CHANGES_PER_METRIC` by absolute delta) and the **lowest / highest value** (only if it is the extreme of every reported annual value and the year frames). Every candidate is a `RunRequest` **validated by the framer itself** (kind as intended, relative change ≥ `MIN_RELATIVE_CHANGE` 1%); neutral wording (differ / rise / fall / was). `latest_change(entity, source, metric, asker=)` → the most recent validated change (the scope check's past-period alternative). `CachingSource` memoises the series. |
| `agents/scope.py` | Scope check after `resolve_entity`, before Loop A. `check(request, resolution, sample=, source=, discovery=callable, tracer=, today=None)` → `ScopeCheck`. Reasons: `forecast` (`forward_cue(question)`: strong cues "what if", "will", "going to", "suppose", "what/how would" or "would … if" without a "have" within three words, always; weak cues "forecast", "predict", "projection", "outlook", "expect … to", "next year/quarter" only when the question is not framed as explaining the past, "Why did …"; or a period ending after today), `not-sec-registrant` (live `EntityNotFound` with zero `sec_tickers` rows, never when degraded), `not-in-sample` (sample). Up to `MAX_ALTERNATIVES` (3) runnable `RunRequest`s: registrants **named in the question** (capitalised phrases, `name_phrases`, each matching exactly one CIK in `sec_tickers`), the **same entity, past period**, **same SIC peers** among registered entities (`discovery.registrant` → `sic`, at most `MAX_PEER_PROBES`, cached). Registered → `suggester.latest_change`; unregistered (live) → the fiscal year between its two latest 10-K report dates, `registered: false` (the run registers it). |
| `agents/framer.py` | `frame(request, source, tracer)` → `Frame`: a like-for-like effect. `restatement` when `compare.filing_a/filing_b` are `"<form> filed YYYY-MM-DD"` (same period, two filings), else `change` (period vs prior period, both from the first annual filing reporting the period). Raises `FrameFailure` (metric not in sources → evidence-frontier) or `LoopError`. |
| `agents/hypothesiser.py` | Rule-based (ADR-0007). `propose(frame, parent, path_variables, max_branches=, tracer=, exclude=)` → `Candidate`s from generic rules in `agents/knowledge.py`: hierarchy children, event concepts (goodwill impairment), 8-K items (2.01 disposal, 4.02 non-reliance / 10-K/A), concept switch, restated comparative. No cycles, capped. `prefer=[(rule, key, memory_id)]` (from `memory.preferences()`): candidates whose `knowledge.step_key` matches are kept first within the cap and returned (so tested) first with `Candidate.lesson` set and `memory_ids` on their `propose` line; node ids keep the rules' order. When the model lanes are on, the orchestrator then asks `model_lanes.propose` to fill only the slots the rules left free under `MAX_BRANCHES_PER_LEVEL` (also when the rules found none). |
| `agents/analyst.py` | `measure(candidate, frame, source, attempt=, scope=, tracer=)` → `Measurement`: queries only through `EvidenceSource`, keeps SQL + filter + rows per query, computes the candidate's effect and the counterfactual (intervention re-query on the returned rows). Scopes: `broad` → `window` → `relaxed` (set by the critic). A disposal measured on the filer's own disposed-group revenue (`DISPOSAL_MAGNITUDE`) adds a `mechanism` line naming that fact and its filing, so a 100% share reads as measured (B-30). |
| `agents/critic.py` | Pure rules over a `Measurement`: `judge(candidate, m, frame, retries_left=)` → `Verdict` (`accept` / `prune` / `retry` / `frontier`, label, evidence status, share vs the root effect); `apply_gate(verdict, choice)`. Thresholds in `agents/common.py` (`MOST_OF_EFFECT`, `MIN_SHARE`, …). The final verdict (not a retry) may get the deep lane's `model_lanes.second_opinion`; the rule verdict decides, a disagreement goes to `critic_escalation` (proposal `keep-rule`), and `trace_verdict` runs after that, so the critic's line shows the decided verdict. `judge_lesson(node, expected=, exact=, fits=)` → `LessonVerdict(decision support/reject, feedback, conclusive, reason)`: a pruned step rejects the lesson (`wrong` if learnt on the same kind of effect and metric family, else `not_helpful`); conclusive only for the lesson's own step on a fitting question with its recorded outcome (frontier, or accepted with at least `MOST_OF_EFFECT`); `trace_lesson` writes `critic` / `lesson_support` or `lesson_reject` with `memory_ids`. |
| `agents/gap_analyst.py` | `for_candidate(frame, node, tracer)` / `for_variable(...)` / `for_breakdown(frame, ruled_out, tracer)` (every tested candidate was a ruled-out accounting/filing event, `knowledge.EVENT_RULES`: says what was ruled out and asks for `<metric> by segment or product`, relation `same entity, breakdown`; Loop B is skipped for it) → `InformationNeed` (variable + aliases, entity hint from the run's own evidence, period, join key, expected magnitude, the intervention test to run). **Loop B consumes this.** |
| `agents/entity_resolver.py` | Before Loop A. `resolve(request, source=, sample=, tracer=, discovery=callable, views=callable)` → `Resolution(entity, registered, reason, error_type, evidence, candidates)`. ## Run phases (for UI)
Every slow phase is bracketed by trace lines on the SSE stream (`GET /runs/{id}/events`): `agent: "orchestrator"`, `action: "phase_start"` / `"phase_done"`, field `phase` (below), `target_agent` (the agent doing the work), `duration_ms` and `status` on `phase_done` (plus `outcome` / `end_state` where useful); while a phase runs, `action: "heartbeat"` with the same `phase` and `elapsed_ms` every `PHASE_HEARTBEAT_SECONDS` (default 5), so no wait is silent for more than ~5 s. Nested phases close before their parent. Measured live on 2026-10-23 ([docs/measurements/live-any-company.md](docs/measurements/live-any-company.md)); sample mode runs every phase in milliseconds.

## External services (live mode only; sample mode needs none)
- **Zetaris**: local Docker bundle at `~/Repos/hackathon2026/zetaris/zetaris-platform` (2.4.3.1-hackathon). REST `http://localhost:8888/api/v1.0`, or `http://host.docker.internal:8888/api/v1.0` from containers. `POST /sql-editor/sqls/run` with `Authorization: Bearer`, `X-Org-ID: 1` and a fresh `X-Request-ID` UUID. `bootstrap` registers database `TIRESIAS_SEC`, container `tiresias`, raw REST tables `TIRESIAS_SEC.<ticker>_{facts,submissions}_raw` and views `tiresias.<ticker>_<concept slug>` / `tiresias.<ticker>_filings` for `ge`, `gehc`, `gev`. The older probe views `ge_revenue_cf` and `gehc_revenue` still exist but are unused.
- **Meterless Nightshift**: runs in an isolated macOS VM, because the installer is ad-hoc signed and not notarized. It's an OpenAI-compatible Runtime reached through hotspot mode at the VM's IP. Headers: `meterless-app: tiresias`, `meterless-scope: user`. Models: `meterless/fast`, `meterless/deep` (lanes, not model ids: on 1.2.1 the receipt named `nvidia/nemotron-3.5-lightning-30b-a3b`, `-3.5-super-vl-120b-a12b` and `-3-ultra-550b-a55b` on different calls of the same lanes, so the trace logs `routed_model` from the receipt; 1.2.4 honours `METERLESS_MODEL_FAST` / `METERLESS_MODEL_DEEP` set to a model id, e.g. `nvidia/nemotron-3.5-lightning-30b-a3b` / `nvidia/nemotron-3-ultra-550b-a55b`). Timeout 180 s (`MODEL_TIMEOUT_SECONDS`), capped by the model lanes at the run budget left. The NVIDIA key lives **only** in Nightshift.
